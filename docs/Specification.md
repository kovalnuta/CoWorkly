# Спецификация требований 0.1

**Проект:** CoWorkly — система бронирования рабочих мест в коворкинге  


## 1. Назначение продукта

CoWorkly — настольное приложение для бронирования рабочих мест в коворкинге. Решает задачу быстрого поиска и занятия свободного места без бумажного журнала и звонков администратору.

Предоставляет интерактивную карту здания с трёхуровневой навигацией (этаж → комната → место), авторизацию, бронирование с проверкой конфликтов и хранение данных в PostgreSQL в Docker.

Результат для пользователя: за несколько кликов найти свободное место и закрепить его за собой на 2 часа.

## 2. Пользователи

- **Клиент** — сотрудник коворкинга или гость. Регистрация, вход, просмотр карты, бронирование, отмена.
- **Администратор** — управляющий. В MVP действует как клиент. В резерве — управление пользователями, комнатами, местами.
- **Разработчик** — ведёт репозиторий через ветки и PR, следит за CI.

## 3. Основной сценарий

1. Запуск приложения.
2. Окно входа с вкладками «Вход» и «Регистрация».
3. Регистрация: система проверяет данные и создаёт аккаунт.
4. Вход: система проверяет логин и пароль, открывает главное окно.
5. Выбор этажа → комнаты → места.
6. Клик по свободному месту создаёт бронь на 2 часа, место становится голубым.
7. Повторный клик по своей брони — отмена.
8. Клик по чужому месту — сообщение «занято».
9. «Назад» — возврат на уровень выше.
10. «Выйти» — конец сессии.

## 4. Обработка ошибок

- Пустые поля при входе → «Введите имя пользователя и пароль».
- Пользователь не найден → «Пользователь с таким именем не найден».
- Неверный пароль → «Неверный пароль».
- Пустое поле при регистрации → сообщение под полем.
- Короткий username → «Имя пользователя должно быть не короче 3 символов».
- Кириллица в username → «Только латинские буквы, цифры и подчёркивание».
- Некорректный email → «Некорректный email: ...» с указанием причины.
- Чужой домен email → список разрешённых доменов.
- Слабый пароль → сообщение о конкретном требовании.
- Несовпадение паролей → «Пароли не совпадают».
- Дубликат username или email → «Уже существует».
- Попытка занять занятое место → «Место A1 уже занято».
- Ошибка подключения к БД → приложение не запускается, сообщение Npgsql.
- Конфликт портов PostgreSQL → сообщение в логе.

## 5. Функциональные требования

**FR-01. Регистрация.**
Условие: заполнена форма и нажата кнопка. Действие: проверка username (латиница, 3+, уникальность), email (валидный домен, уникальность), пароля (8+, верхний и нижний регистр, цифра, спецсимвол), совпадения паролей. Результат: пользователь создан с ролью Client, пароль сохранён как BCrypt-хеш, открыто главное окно.

**FR-02. Вход.**
Условие: введены логин и пароль. Действие: поиск пользователя, проверка через `PasswordHasher.Verify`. Результат: при верных данных — главное окно, при неверных — сообщение под полем.

**FR-03. Хеширование паролей.**
Условие: регистрация. Действие: BCrypt с солью. Результат: в `PasswordHash` строка с `$2a$`, отличная от пароля.

**FR-04. Просмотр этажей.**
Условие: пользователь вошёл. Результат: три этажа с номерами и описаниями.

**FR-05. Просмотр комнат.**
Условие: выбран этаж. Результат: список комнат с названиями и вместимостью.

**FR-06. Просмотр мест.**
Условие: выбрана комната. Результат: сетка мест с цветом: бежевый — свободно, голубой — моя бронь, розовый — занято.

**FR-07. Бронирование.**
Условие: клик по свободному месту. Действие: бронь на 2 часа от текущего момента. Результат: место голубое, сообщение в статусной строке.

**FR-08. Отмена брони.**
Условие: клик по своему месту. Результат: бронь удалена, место бежевое.

**FR-09. Защита от конфликтов.**
Условие: клик по чужому месту. Результат: бронь не создаётся, «Место занято».

**FR-10. Сохранение данных.**
Условие: перезапуск. Результат: данные в PostgreSQL, доступны после запуска.

**FR-11. Веб-версия на Java (резерв).**
Условие: после MVP. Результат: бронирование через сайт.

## 6. Нефункциональные требования

**NFR-01. Автоматическая сборка.**
Push в ветку или PR в master → GitHub Actions собирает проект, результат в PR, при падении мерж блокирован.

**NFR-02. Безопасность строки подключения.**
Строка в `appsettings_new.json`, файл в `.gitignore`, пароля в репозитории нет.

**NFR-03. Схема базы через миграции.**
`context.Database.Migrate()` применяет миграции, данные не теряются.

**NFR-04. Работа с временем.**
В базе UTC, на экране локальное через `.ToLocalTime()`. Ошибки сравнения timestamp не возникает.

**NFR-05. Сборка на Windows-раннере.**
Workflow на `windows-latest`, потому что WPF не собирается на Linux.

## 7. MVP и резерв

**MVP:** регистрация с валидацией, вход, BCrypt-хеширование, просмотр этажей, комнат и мест, бронирование на 2 часа, отмена, защита от чужих броней, сохранение в PostgreSQL, CI, миграции EF Core.

**Резерв:** управление пользователями для Admin, календарь, продление брони, восстановление пароля, тёмная тема, экспорт в CSV, веб-версия на Java, мобильное приложение.

## 8. Правила репозитория и DoD

**Защита ветки.** `master` защищена, прямой push запрещён, только через PR.

**Ветки.** Каждая задача — issue. Под неё ветка с префиксом `feature/`, `fix/` или `chore/`. После завершения — PR в `master`.

**Проверки.** На каждый push и PR запускается GitHub Actions `Build` на Windows-раннере. При падении сборки PR слить нельзя.

**Required checks.** PR не сливается, пока проверки не пройдены.

**Коммиты.** Conventional Commits: `feat`, `fix`, `chore`, `docs`, `style`, `refactor`.

**DoD.** Задача выполнена, когда: код написан и работает; собирается локально; закоммичен с осмысленным сообщением; ветка запушена; PR создан и описан; CI зелёный; PR слит; issue закрыта; локальный `master` обновлён.

**Пример.** Issue #6 «Set up GitHub Actions CI/CD for build checks» → ветка `feature/ci-build` → коммит `ci: add GitHub Actions build workflow` → PR #7 → CI зелёный → merge → issue #6 закрылась по `Closes #6` → локальный `master` обновлён.

## 9. Исходное состояние для проверки

**Данные.** Создаются автоматически в `SeedData`: `Anna` (Admin) и `Kirill` (Client) с паролем `Passw0rd!`, три этажа, семь комнат, сетки мест. Дополнительные данные — через форму регистрации.

**Конфигурация.** Строка подключения в `appsettings_new.json`, файл в `.gitignore`, шаблон — `appsettings.Example.json`. База поднимается через `docker compose up -d`.

**Ресурсы.** Windows 10/11, .NET 8 SDK, Docker Desktop, Visual Studio 2022 или Rider, DBeaver (опционально), аккаунт GitHub.

**Безопасность.** Пароль БД не в коде и не в репозитории. Пароли пользователей — только BCrypt-хеши. Локальный PostgreSQL остановлен, чтобы не конфликтовать с Docker. `coworkly_pass` — учебный, для продакшна не подходит.

## 10. Системное программирование

В качестве направлений системной сложности рассматриваются интеграция с внешним API и работа с миграциями базы данных. Первый модуль для реализации — сервис уведомлений, который при бронировании места отправляет сообщение во внешний сервис через HTTP.
